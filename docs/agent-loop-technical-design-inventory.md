# Harness Agent Loop 技术设计盘点

> 文档状态：设计盘点 / 待评审  
> 适用范围：`harness` 中负责一次 Agent 任务执行的循环内核及其直接依赖  
> 当前基线：Rust 标准库实现的同步版 Agent Loop 初稿

## 1. 目标与边界

### 1.1 目标

Agent Loop 应该负责把一次用户任务转换为可控、可观测、可恢复的执行过程：

```text
用户请求
   ↓
创建 Session / Run
   ↓
准备上下文
   ↓
模型决定下一步动作
   ↓
校验权限与预算
   ↓
执行工具或返回结果
   ↓
记录状态、事件和轨迹
   ↓
继续循环 / 暂停 / 结束 / 失败
```

核心要求：

- 模型提供商可替换，不把具体 SDK 绑定到循环内核。
- 工具可以是本地函数、进程、远程服务或 MCP 工具。
- 一次运行有明确的终止条件、资源边界和错误语义。
- 执行过程可追踪、可测试，并为后续持久化和 RSI 改进保留数据。
- 默认安全，危险操作必须经过权限、审批或沙箱边界。

### 1.2 非目标

以下能力不应直接塞入第一版 Loop：

- 具体模型 Prompt 的编排策略。
- 某个模型厂商的请求格式或 SDK 类型。
- 复杂的长期记忆实现。
- 完整的任务调度平台和分布式队列。
- 自动修改自身代码的闭环。

这些能力应通过 Adapter、Store、Policy 和上层 Orchestrator 接入。

## 2. 当前实现基线

当前 `harness` 已有以下抽象：

| 抽象 | 当前职责 | 后续需要演进的方向 |
| --- | --- | --- |
| `Model<S>` | 根据状态和上下文返回 `Action` | 异步、流式、结构化响应、模型路由 |
| `Tool<S>` | 使用输入修改状态并返回字符串 | Schema、权限、超时、取消、沙箱 |
| `ToolRegistry<S>` | 按名称注册和查找工具 | 版本、能力声明、生命周期、远程工具 |
| `Observer` | 接收 Agent 事件 | 事件总线、指标、Trace、可靠投递 |
| `DecisionContext` | 向模型提供 Prompt、步数和历史 | 分层上下文、Token 预算、压缩和脱敏 |
| `RunResult` | 表示完成或达到最大步数 | 更完整的终止原因、恢复点和输出类型 |

当前实现适合验证控制流，但还不适合生产使用，尤其缺少异步边界、权限、持久化、超时和取消。

## 3. 核心领域模型

### 3.1 关键实体

- **Agent**：可执行的智能体定义，包含模型、系统规则、工具集合和策略。
- **Session**：用户与 Agent 的长期会话，包含跨 Run 的上下文和记忆引用。
- **Run**：一次用户请求触发的执行实例，应有唯一 `run_id`。
- **Step**：一次模型决策及其对应的工具执行或结束动作。
- **Action**：模型请求执行的动作，例如工具调用、最终回答、等待用户或转交其他 Agent。
- **Tool**：可被 Agent 调用的能力，包含输入契约、权限要求和执行器。
- **Policy**：对模型输出、工具调用、数据访问和资源消耗的约束。
- **Trace/Event**：描述执行过程的不可变记录，用于调试、审计、评估和 RSI。

### 3.2 建议的终止原因

不能只用“成功/达到最大步数”表达 Run 结果，建议至少区分：

- `Completed`：Agent 正常返回最终结果。
- `NeedsUserInput`：需要用户补充信息或审批。
- `Cancelled`：用户或系统主动取消。
- `TimedOut`：超过时间预算。
- `BudgetExceeded`：超过步数、Token、费用或工具调用预算。
- `PolicyDenied`：策略拒绝了动作。
- `ToolFailed`：工具执行失败且无法恢复。
- `ModelFailed`：模型请求失败且无法恢复。
- `ContextOverflow`：上下文无法继续容纳。
- `MaxStepsReached`：达到循环步数上限。
- `SystemFailed`：基础设施或内部错误。

## 4. Loop 控制流设计

### 4.1 一次 Step 的推荐顺序

```text
1. 检查 Run 是否已取消、超时或超预算
2. 构造本次模型上下文
3. 调用 Model Adapter
4. 解析并校验模型动作
5. 运行 Policy / Permission 检查
6. 记录 ActionSelected
7. 执行 Tool / Delegate / Wait / Finish
8. 记录结果、耗时、资源消耗和错误
9. 更新短期上下文与记忆候选
10. 判断是否继续、暂停、恢复或结束
```

顺序需要固定并形成测试契约，避免出现“工具已执行但没有审计记录”或“超时检查滞后导致额外调用”等问题。

### 4.2 Loop 状态机

建议把隐含的 `for` 循环显式建模为状态机：

```text
Created
  → Running
  → WaitingForModel
  → ValidatingAction
  → WaitingForApproval
  → ExecutingTool
  → RecordingResult
  → Running

Running → Completed / Failed / Cancelled / TimedOut / Paused
Paused  → Running / Cancelled / Expired
```

显式状态机有利于：

- 支持人工审批和异步工具。
- 在进程重启后恢复 Run。
- 防止重复执行工具。
- 做状态迁移校验和审计。

### 4.3 继续条件与防循环

除了最大步数，还需要考虑：

- 相同 Tool + 相同输入连续调用次数。
- 状态没有变化但模型反复请求同一动作。
- 失败重试次数。
- 总耗时、Token、费用和工具调用数量。
- 单个工具和整次 Run 的预算。
- 模型返回非法动作或空动作。

建议给每种限制独立配置，并在 `RunResult` 中返回触发的具体原因。

## 5. Model Adapter 设计

### 5.1 内核接口与模型协议解耦

Loop 不应直接处理厂商响应，而应通过 Adapter 转换为内部协议：

```text
Provider SDK Response
        ↓
Model Adapter
        ↓
Internal ModelOutput
        ↓
Action Parser / Validator
        ↓
Action
```

内部协议至少应包含：

- 文本增量或最终文本。
- Tool Call：名称、调用 ID、结构化参数。
- 模型停止原因。
- Token 使用量和模型信息。
- 原始响应引用或脱敏后的调试信息。

### 5.2 同步、异步和流式

当前同步 Trait 适合最小原型，但生产形态建议支持：

- `async` 模型调用，避免阻塞线程。
- 流式文本和 Tool Call 增量。
- 取消令牌传递到模型请求。
- 请求超时和指数退避。
- 可重试错误与不可重试错误分类。
- 模型路由和故障转移。

建议先稳定领域类型，再选择 async runtime 和 HTTP/SDK 依赖。

## 6. Action 与 Tool 设计

### 6.1 Action 类型

建议将 `Action` 从简单的字符串工具调用扩展为结构化枚举：

- `CallTool { call_id, name, arguments }`
- `Finish { output }`
- `AskUser { question, schema }`
- `Delegate { agent_id, input }`
- `SleepUntil { deadline }`
- `Noop` 或拒绝非法动作

所有 Action 都应保留 `step_id`、`run_id` 和可选的模型来源信息。

### 6.2 Tool 描述信息

Tool 不应只有 `name()` 和 `execute()`，还需要描述：

- 稳定 ID、版本和展示名称。
- 输入 Schema 和输出 Schema。
- 所需权限和敏感数据范围。
- 是否有副作用、是否幂等。
- 是否支持取消、超时和重试。
- 资源需求和费用估计。
- 是否允许在本地、远程或沙箱执行。

### 6.3 工具执行语义

必须明确以下问题：

- Tool 失败是否允许模型重试？最多几次？
- 超时后工具是否可能仍在后台执行？
- 进程被杀后如何判断副作用是否发生？
- 重试是否需要幂等键？
- 工具输出过大时如何截断、摘要或存储外部引用？
- 工具是否可以修改 Agent 主状态，还是只能返回事件？

涉及文件、网络、支付、删除、发送消息等副作用的工具，应优先采用幂等键、预览、审批和可回滚设计。

## 7. 状态、上下文与记忆

### 7.1 分离三类状态

建议不要把所有数据都放在泛型 `S` 中，而是区分：

1. **运行状态**：本次 Run 的临时数据和工具结果。
2. **会话状态**：用户与 Agent 的短期连续对话上下文。
3. **长期记忆**：需要经过筛选、授权、持久化和检索的数据。

这样可以分别处理生命周期、权限、压缩和一致性。

### 7.2 Context 组装

上下文建议按优先级分层：

```text
系统规则 / 安全策略
用户 Profile
当前用户请求
当前 Run 的工具结果
相关 Session 历史
检索到的长期记忆
工具描述
```

需要设计：

- Token 预算和估算方式。
- 历史压缩、摘要和丢弃策略。
- 敏感信息脱敏。
- 记忆来源和可信度标记。
- 模型看到的上下文与审计保存的上下文是否一致。

### 7.3 一致性

工具可能修改外部世界，而模型上下文是旧快照，因此需要：

- 工具结果作为事实来源写入 Step。
- 必要时重新读取外部状态。
- 对关键资源使用版本号或乐观锁。
- 记录状态快照或可重放事件。

## 8. 权限、安全与沙箱

这是 Harness 的核心设计点，不应作为后置功能。

### 8.1 权限决策链

推荐的调用链：

```text
模型动作
  → Tool Schema 校验
  → Agent 权限
  → 用户权限 / 设备权限
  → 数据范围检查
  → 风险分级
  → 自动执行 / 请求审批 / 拒绝
```

### 8.2 风险分级

- **低风险**：只读、无敏感数据、无外部副作用。
- **中风险**：访问个人数据、网络请求、创建文件、启动进程。
- **高风险**：删除、发送消息、支付、修改权限、执行任意代码。

高风险工具应具备明确的用户确认、参数展示和审计记录。

### 8.3 沙箱边界

需要明确：

- 文件系统允许访问的目录。
- 网络域名和端口白名单。
- 环境变量和凭据注入方式。
- CPU、内存、磁盘、进程和时间限制。
- 子进程回收和僵尸进程处理。
- 输出和错误日志的敏感信息清理。

## 9. 可靠性与错误处理

### 9.1 错误分类

建议将错误拆为：

- 输入错误：Prompt、Action、Tool 参数非法。
- 策略错误：权限拒绝、预算超限。
- 暂时性错误：网络抖动、限流、服务暂不可用。
- 永久性错误：工具不存在、参数不符合 Schema。
- 外部副作用不确定：超时但可能已执行。
- 内部错误：状态损坏、序列化失败、程序 Bug。

不同分类应对应不同策略，不能统一简单地重试。

### 9.2 重试与幂等

每次重试应记录：

- 原始调用 ID 和重试序号。
- 触发原因和等待时间。
- 是否确认上一次调用未产生副作用。
- 最终采用的结果。

对有副作用的工具，必须优先使用幂等键或状态查询，而不是盲目重试。

### 9.3 恢复与持久化

如果要支持进程重启后恢复，至少需要持久化：

- Run 元数据和状态。
- 已提交的 Action。
- 工具调用状态：待执行、执行中、成功、失败、未知。
- 上下文版本或事件序列号。
- 取消和审批状态。

推荐采用事件日志或明确的 Checkpoint，而不是只保存最后一份可变状态。

## 10. 并发、异步工具与 Agent Delegation

### 10.1 第一阶段建议

先保持单 Run、单 Step 串行执行，确保状态和审计语义稳定。

### 10.2 后续并发模型

并发工具调用需要额外设计：

- 工具是否读取或写入同一状态。
- 如何限制并发数。
- 结果返回顺序是否稳定。
- 一个工具失败时是否取消其他工具。
- 部分成功如何呈现给模型。
- 事件和 Trace 如何关联多个子任务。

### 10.3 Delegation

Agent 委托应视为一种受控 Tool/Action，而不是直接递归调用：

- 子 Agent 有独立权限和预算。
- 父子 Run 具备关联 ID。
- 明确输入、输出和最大深度。
- 防止 Agent 间无限递归。
- 子 Agent 的工具调用不能绕过父级策略。

## 11. 可观测性、审计与 RSI 数据

### 11.1 事件模型

至少需要记录：

- Run 创建、开始、结束和终止原因。
- 模型请求开始、结束、耗时、模型名和 Token。
- Action 原文、解析结果和校验结果。
- 权限决策和审批结果。
- Tool 开始、结束、耗时、重试和输出摘要。
- 状态/上下文版本。
- 错误堆栈和外部请求关联 ID。

### 11.2 数据分级

需要区分：

- 可用于在线调试的日志。
- 受权限控制的审计记录。
- 用于评估和 RSI 的脱敏 Trace。
- 不应持久化的密钥、个人隐私和完整工具输出。

### 11.3 指标

建议从第一版建立：

- Run 成功率和各终止原因占比。
- 平均/分位数延迟。
- 模型调用次数、Token 和费用。
- Tool 成功率、重试率和超时率。
- 用户打断率和审批拒绝率。
- 上下文溢出率。
- Agent 自主完成率和人工接管率。

这些数据也是后续 Scorer、Proposer 和 RSI 流程的基础。

## 12. 测试策略

### 12.1 单元测试

覆盖：

- 正常 Tool → Finish 流程。
- 最大步数和各类预算限制。
- 空名称、重复工具、未知工具。
- 非法 Action 和非法参数。
- Model、Tool、Observer 错误传播。
- 取消、超时和重试状态转换。
- 上下文压缩与敏感信息脱敏。

### 12.2 属性与不变量测试

重点验证：

- Step 序号单调递增且不重复。
- 工具未通过 Policy 时不会被执行。
- 终止后的 Run 不会继续产生工具调用。
- 同一幂等键不会造成重复副作用。
- 预算不会被绕过。
- 每个已执行工具都有对应的开始/结束或未知状态记录。

### 12.3 集成测试

使用 Fake Model、Fake Tool、Fake Clock 和 Fake Store 测试：

- 模型服务失败重试。
- 工具超时与取消。
- 进程重启后的恢复。
- 审批暂停和恢复。
- 多 Agent 委托。
- 事件投递失败时的降级策略。

### 12.4 评估测试

后续需要单独建立任务集，评价：

- 工具选择正确率。
- 参数正确率。
- 无谓调用率。
- 任务完成率。
- 安全策略绕过率。
- 轨迹质量和成本。

## 13. 推荐模块拆分

建议逐步演进为以下模块，而不是把逻辑继续堆在 `loop_engine.rs`：

```text
harness/src/
├── action/          # Action、Schema、解析与校验
├── context/         # 上下文组装、压缩、脱敏
├── error/           # 分层错误和终止原因
├── event/           # 事件、Trace、Observer
├── execution/       # Tool 执行、超时、重试、取消
├── loop_engine/     # 状态机和 Step 调度
├── model/           # Model Trait 与 Provider Adapter
├── policy/           # 权限、预算、审批、风险分级
├── state/           # Run/Session 状态和 Checkpoint
├── storage/         # Event Store、Memory Store、Trace Store
└── tool/            # Tool 描述、注册、生命周期和路由
```

## 14. 分阶段实现建议

### Phase 1：稳定同步内核

- 明确 `Action`、`RunResult`、`TerminationReason`。
- 为 Tool 增加结构化描述和基本参数校验。
- 增加 Fake Model、Fake Tool、Fake Observer 测试设施。
- 增加统一的 Step/Run ID 和事件序列。
- 增加取消、超时和预算接口，但可先使用同步实现。

### Phase 2：策略与可靠性

- 引入 Policy/Permission 层。
- 增加重试、幂等键和失败分类。
- 增加 Checkpoint 和内存 Event Store。
- 增加审批暂停/恢复。
- 完善 Trace、指标和敏感信息处理。

### Phase 3：异步与外部集成

- 切换到 async Model/Tool 接口。
- 接入具体模型 Provider、MCP 和远程工具。
- 支持流式输出、工具超时和取消传播。
- 接入沙箱、进程执行和设备路由。

### Phase 4：多 Agent 与 RSI

- 引入 Delegation 和父子 Run。
- 建立脱敏 Trace 数据集和离线评估。
- 实现 Scorer、Proposer 和策略验证闭环。
- 增加 Agent Market、版本管理和兼容性策略。

## 15. 第一版建议决策

为了控制复杂度，建议下一步先做以下明确决策：

1. 保持单线程、单 Run、串行 Tool 执行。
2. 将 `Action` 和 Tool 参数升级为结构化类型，预留 JSON Schema，但暂不绑定具体协议。
3. 增加 `run_id`、`step_id`、终止原因和事件序列号。
4. 将 Policy 检查放在 Tool 执行之前，任何工具不能绕过该入口。
5. 为超时、取消、重试和预算定义接口，先用可测试的 Fake 实现。
6. 将状态、上下文和长期记忆分开建模。
7. 使用 Fake Model/Tool/Clock/Store 建立确定性测试，不依赖真实网络和模型。
8. 暂不引入过多依赖，待异步、序列化和持久化边界明确后再选择库。

## 16. 需要尽早确认的问题

- Agent Loop 是库、独立进程，还是 Harness 内的服务组件？
- Run 是否要求进程重启后恢复？
- Tool 是否允许直接修改共享状态？
- 哪些工具需要用户审批？审批由 UI 还是 Server 负责？
- 是否要求离线本地模型和云端模型统一接口？
- Trace 是否允许保存完整 Prompt、工具参数和输出？
- RSI 是否使用线上真实用户轨迹，若使用，如何脱敏和获得授权？
- Agent Delegation 的边界是递归调用、消息队列，还是独立 Run？
- 目标设备是否包含资源受限的手机、汽车或嵌入式设备？

这些问题会直接影响状态持久化、调度模型、权限架构和依赖选择，应在进入异步化和远程工具开发前完成一次评审。
