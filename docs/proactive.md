# 通用主动任务与通知

每个成功结束的用户 Turn 都在后台进入一次任务提取队列。端侧模型读取该轮 query、已确认记忆和现有任务，静默判断是否应创建、更新、取消任务；普通问答输出 `none`。提取结果必须包含 query 原文证据，时间和重复规则也必须能在 query 或已确认记忆中找到依据。每轮最多生成一条任务，已处理的 Turn 不重复提取。模型暂时失败时保留队列，在下次启动或下一轮对话后重试。桌面端仅使用本机模型地址执行提取，iOS 使用已导入的端侧模型。

主动发现不依赖新 Turn。App 运行期间每 30 分钟调用一次后台扫描；Rust 持久化最近扫描时间，避免重复调用端侧模型。扫描读取已有记忆和已连接的查询工具，可在用户没有提过“提醒”或“下雨”时，根据稳定下班时间与天气工具建立条件检查任务。到点后查询实时天气，仅在条件成立且建议仍有价值时推送。提取器拒绝保存模型虚构的工具名；没有稳定检查时间或可用实时工具时不创建任务。同一记忆与检查时间不会反复生成任务，用户删除后也会记住该来源已被拒绝。

Turn 触发与后台扫描都只负责建立未来的检查计划，不负责感知未来的天气。天气突然变化时立即触发的事件订阅仍未实现。

每条任务保存稳定 ID、名称、执行指令、记忆检索关键词、允许调用的查询工具名、推送前至少一个必须成功调用的工具名，以及一次性事件时间或当地每周重复时间、提前启动分钟数和截止分钟数。用户通过“主动任务”页面查看、停用或删除自动生成的任务。饭点、通勤只是可迁移的旧任务，不再是调度器允许的仅有场景。

任务保存在本地 SQLite `proactive_tasks`，已提取 Turn 保存在 `proactive_planned_turns`。升级时将历史已完成 Turn 标记为已处理，避免追溯生成旧任务。启动时会把旧 `proactive_rules` 中的饭点和通勤配置一次性迁移，保留原时间与开启状态。运行记录保存在 `proactive_runs`，以任务 ID 和事件时间去重。修改或删除任务会使其未投递结果失效。

App 启动、设置变化或定时器唤醒时刷新设备时区偏移。App 读取所有任务的下一次执行时间、失败重试时间和结果过期时间，等待最近的一个时间点；没有待执行任务时停止等待。到点后 Rust 在事务中领取任务并规划该任务下一次运行。任务失败后在 5 分钟后、截止前可重新领取；App 调度出错则在 1 分钟后重试。

领取任务后，Harness 启动独立、静默的多步 Agent Loop。它按该任务的关键词检索有效记忆，只披露任务明确允许的工具，并把名称、指令和时间窗口传给模型。MCP 工具仍经过原有审批流程。最多执行 5 步，截止时间到达即停止。模型输出 `push/skip`；配置了必需工具时，至少一个工具成功返回才允许推送。没有成功的实时工具结果时，通知文案只能使用任务名称和通用的打开 App 建议，避免编造天气、商家、价格或时效。后台不会下单、付款或叫车。

结果先保存为 `ready`。App 检查通知权限并提交系统通知，成功后才标记为 `delivered`。iOS 在首次自动创建启用任务时申请通知权限，桌面 JVM 使用系统托盘通知。推送动作固定为打开 App。

## 当前边界

- 定时等待与端侧推理依赖 App 进程运行。iOS 关闭 App 后的准时推送仍需要服务端调度和远程推送链路。
- 后台机会扫描的间隔是 30 分钟；固定行程前的实时条件检查由任务本身的唤醒时间触发。App 休眠时扫描和本地模型运行可能延迟。
- 工程尚无内置天气、餐厅、配送或打车数据源。需要实时依据的任务应配置相应查询工具和必需工具；工具未连接时会跳过。
- 支持一次性时间和按当地时间每周重复，重复规则支持任意星期组合。地点或外部事件触发器尚未接入。设备时区偏移在启动、设置改变或下一次定时器唤醒时刷新。
- 查询工具名称由模型从当前 MCP 工具清单中选择，并限制为查询类名称；工具用途仍需在 MCP 集成处核验，外部调用受 MCP 审批约束。
- 端侧模型输出的相对日期会校验当天、明天和后天；任意自然语言日期、中文时分与模型输出时间的一致性尚需更完整的解析器。
- Android 尚无可用 App MVP，因此没有 Android 通知投递实现。
